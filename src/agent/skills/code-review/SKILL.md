# Code Review

对用户提交的代码进行系统性审查，输出清晰、可落地的改进建议。

## 工作流程

1. **理解上下文**：先判断代码的语言、用途和审查重点。若用户未说明，默认做全面审查；若用户指定了方向（"只看安全性"、"主要看性能"），则聚焦该方向。
2. **多维度扫描**：按下方检查清单逐维度过一遍代码，记录发现的问题和亮点。
3. **整理优先级**：按严重程度（阻塞 / 建议 / 可选）对问题分级，不要把所有问题一视同仁地堆给用户。
4. **产出报告**：用下面的格式输出审查结果，附上可直接应用的修改建议。

## 检查清单

### 正确性
- 逻辑是否符合预期？边界条件、空值、越界是否处理？
- 循环、递归有无终止条件缺失或死循环风险？
- 异步代码（Promise、async/await）是否正确处理错误和竞态？

### 安全性
- 用户输入是否经过验证和转义（防 SQL 注入、XSS 等）？
- 敏感信息（密码、Token、密钥）是否硬编码或泄露到日志？
- 权限校验是否缺失或过于宽松？

### 可读性与可维护性
- 命名是否清晰表达意图？
- 函数 / 类职责是否单一？是否有过长的函数（超过 50 行需关注）？
- 重复代码是否可提取为公共函数？
- 注释是否解释了"为什么"而不只是"是什么"？

### 性能
- 是否有不必要的计算、重复查询或内存泄漏风险？
- 数据结构选择是否合适？循环嵌套是否可以优化？
- 对大数据集是否有分页、懒加载或流式处理？

### 工程规范
- 是否符合项目既有的风格约定（命名、缩进、导入顺序）？
- 错误处理是否统一？是否有裸 `catch` 吞掉错误？
- 测试覆盖是否充分？关键分支是否有对应用例？

## 输出格式

```
## 代码审查报告

### 总体评价
一段话概括代码质量和主要关注点。

### 🔴 阻塞问题（必须修改）
> 影响正确性或安全性，合并 / 上线前必须解决。

**问题 1**：[简短标题]
- **位置**：第 XX 行 / `函数名`
- **描述**：说明问题是什么、为什么危险。
- **建议**：
  \```language
  // 修改后的代码示例
  \```

### 🟡 建议改进（应当修改）
> 不影响运行但会降低可维护性或性能。

**建议 1**：[简短标题]
- **位置**：...
- **描述**：...
- **建议**：...

### 🟢 可选优化（锦上添花）
> 更好的写法，但优先级低，视时间决定是否处理。

**优化 1**：...

### ✅ 做得好的地方
列出值得保留或值得表扬的代码实践。
```

## 原则

- **问题必须可操作**：每条问题都要给出具体修改方向或代码示例，不要只说"代码不够好"。
- **严重程度要诚实**：不要把所有问题都标 🔴，也不要为了"友好"把真正的安全漏洞标为 🟢。
- **聚焦用户关心的**：若用户只要求检查某一方面，其余方面简要带过即可，不要喧宾夺主。
- **尊重既有风格**：如果整个项目都用某种约定，不要因为个人偏好要求全部改写。
- **只改被要求的范围**：审查报告是建议，不是重写。除非用户要求，否则不要输出完整重构后的代码。
